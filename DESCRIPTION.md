# Пиячок — опис проєкту

**Пиячок** — вебплатформа для пошуку й обговорення закладів (бари, клуби, караоке, resto-бари тощо): каталог із фільтрами і сортуванням, відгуки з фото чека, новини закладів, обране, зустрічі («пиячки»), листування з менеджерами закладів і підтримкою, скарги, аналітика та дві адмінські панелі (кабінет власника закладу і супер-адмінка).

Проєкт складається з двох частин:

| Частина | Репозиторій | Технології | Порт |
|---|---|---|---|
| Бекенд (REST API) | `backend-final` | NestJS 11, TypeScript, PostgreSQL 16 + PostGIS, Redis, TypeORM | `:3000` |
| Фронтенд (SSR + клієнтська логіка) | `frontend-final` | Next.js 16 (App Router, React Compiler), React 19, Tailwind v4 | `:3001` |

Фронтенд спілкується з API напряму через BFF-проксі (`/api/v1/*` → бекенд, inject JWT з cookie) і напряму — для відображення зображень (`/static/*` rewrite). Детальний опис кожної частини — нижче; про використані технології та їхнє обґрунтування — у `README.md` обох репозиторіїв.

## 1. Роли та права доступу

У системі чотири ролі (RBAC, таблиці `roles` / `permissions` / `user_roles`, RoleGuard через JWT + PermissionsGuard поверх контролерів).

| Роль | Дозволи (permissions) | Як отримується |
|---|---|---|
| `user` | `venue:create`, `review:create`, `review:edit:own`, `hangout:create`, `news:manage:own` | автоматично при реєстрації (`POST /auth/register`) |
| `venue_admin` | усе від `user` + `venue:edit:own`, `analytics:view:own` | автоматично: супер-адмін апрувне заклад (`POST /admin/venues/:id/approve`) → власник отримує роль `venue_admin` |
| `critic` | усе від `user` + `review:feature` | тільки вручну супер-адміном (`POST /admin/users/:id/roles`) |
| `super_admin` | усі 15 permissions (`venue:moderate`, `news:manage:any`, `complaint:manage`, `user:manage`, `analytics:view:all` + інші) | сід при першому запуску (докер-сервіс `migrate`, скрипт `seed-super-admin.ts`) — `admin@gmail.com` / `Admin1234`; перекривається `SUPER_ADMIN_EMAIL` / `SUPER_ADMIN_PASSWORD` |

Кеш дозволів (Redis, TTL 5 хв) інвалідується автоматично за подією `user_role.added`, тож нова роль застосовується одразу. Усі дії супер-адміна над користувачами (зміна профілю, ролей, видалення) пишуться в таблицю `audit_logs`.

**Права діють і на фронті**: кнопки, яких не має роль (наприклад «Виділити відгук» у критика), просто не рендеряться — серверна перевірка прав все одно присутня на кожному ендпоінті.

## 2. Реєстрація та вхід

**Email + пароль:**
- `POST /auth/register` — email, пароль ≥ 8 символів із перевіркою складності, імʼя/прізвище ≥ 2 символів, вік ≥ 18, обовʼязкове прийняття EULA (`acceptEula=true`). Роль — `user`.
- `POST /auth/login` — токени; soft-deleted акаунт (деактивований супер-адміном) при вході паролем оживає.
- Ліміт спроб (throttling): реєстрація 5/год, логін 10/хв, refresh 30/хв, плюс глобальний ліміт 100/хв на всі ендпоінти.

**JWT (access + refresh):**
- access — TTL 15 хв, несе `{sub, email, roles}`; refresh — TTL 30 днів, секрет окремий.
- refresh ротаційний: при `POST /auth/refresh` стара пара відкликається (маркер `revoked:*` у Redis, TTL 30 днів), випускається нова; ролі при refresh перечитуються з БД (відкликування ролі під час сесії спрацьовує на наступному refresh).
- `POST /auth/logout` — ревокація refresh; на клієнті cookie видаляється.

**OAuth:** `GET /auth/google(/callback)`, `GET /auth/facebook(/callback)` — логін через Google і Facebook; калбек редіректить на фронт (`FRONTEND_URL`) з токенами. Ендпоінт `GET /auth/me` повертає повний профіль (email, верифікація, ролі, profile{...}).

**Сесія на фронті:** токени зберігаються лише в httpOnly cookie `piyachok_session` (sameSite=lax, 30 днів, secure у prod); клієнтський JS їх не бачить. Всі API-запити йдуть через BFF-проксі `src/app/api/v1/[...path]/route.ts`, який інжектує `Authorization: Bearer <accessToken>` і автоматично рефрешить токени, якщо access протік.

## 3. Життєвий цикл закладу

Статуси: `pending` → (`approved` | `rejected`); `approved` → `archived`.

1. **Створення.** Залогінений користувач (perm `venue:create`) заповнює форму «Подати заклад»: назва, тип (bar/cafe/restaurant/club/pub), опис, адреса з координатами (для гео-пошуку), контакти, графік роботи, чек, фічі, теги. Заклад створюється у статусі **`pending`** — у публічному каталозі його ще немає.
2. **Фото.** Власник завантажує до 5 фото на заклад (multipart `POST /venues/:id/photos`, білий список MIME jpeg/png/webp, max 5 МБ). Локально — файловий обсяг `uploads/` і роздача `/static/*`; на проді (Vercel) файли йдуть у **Vercel Blob** (`BLOB_STORE_ID` / `BLOB_READ_WRITE_TOKEN`), URL-и — HTTPS від Blob. Окремої модерації фотографій немає — адмін бачить їх у списку заявок.
3. **Модерація.** Перш ніж заклад з'явиться у каталозі, супер-адмін розглядає заявку в адмінці (список `GET /admin/venues/pending`, відсортовано за createdAt ASC):
   - **Затвердити** (`POST /admin/venues/:id/approve`) → статус `approved`, заклад з'являється в каталозі. Одночасно власник автоматично отримує роль **`venue_admin`** (ідемпотентно: якщо уже мав — повторний апрув не дублює) і з цієї миті керує закладом із власного кабінету.
   - **Відхилити** (`POST /admin/venues/:id/reject`) → статус `rejected`. Повідомлення власнику автоматично не надсилається.
   - **Призначити власника** (`POST /admin/venues/:id/assign-owner`) — переназначення власника існуючого закладу на іншого користувача.
4. **Видалення.** Власник (perm `venue:edit:own`) або супер-адмін (`venue:edit:any`) видаляє заклад — це **soft-delete**: статус стає `archived`, заклад пропадає з публічного каталогу, але залишається у базі (історію відгуків/новин не втрачаємо).

**Хто що бачить:**
- публічний каталог і сторінка закладу (`GET /venues`, `GET /venues/:id`) — лише **approved**;
- власник — усі власні заклади будь-якого статусу через `/me/venues` (з бейджами статусу в кабінеті);
- супер-адмін — всі статуси через admin-ендпоінти.

## 4. Каталог і пошук

`GET /venues` — публічний, з пагінацією (десять закладів на сторінку — це і на бекенді, і на фронті). Фільтри:

- **`q`** — вільний пошук (по назві та адресі);
- **`type`** — slug типу (bar, club, pub, restaurant, cafe);
- **`feature`** — CSV фіч (wifi, parking, ...);
- **`tag`** — CSV тегів (коктейлі, кухня, жива музика, більярд...); довідник тегів — `GET /venues/tags` (з кількістю закладів на кожен тег, цим самим на фронті рендерляться чіпи);
- **`minCheck` / `maxCheck`** — діапазон середнього чека;
- **`minRating`** — мінімальний рейтинг (1–5, на фронті — зіркова шкала з кроком 0.5, повторний клік скидає);
- **`lat` / `lng` / `radiusKm`** — геопошук: радіус до точки (PostGIS `ST_DWithin` в метрах, GIST-індекс по `geography(POINT, 4326)`; на фронті кнопка «📍 Поблизу» через `navigator.geolocation`).

Сортування: `rating` | `check` | `newest` | `name` | `distance`. Список закладів кешується в Redis (TTL 60 с) і інвалідується подією при змінах — фільтри/сорти не ламаються.

На фронті каталог — SSR-сторінка `/`: стан фільтрів повністю в URL (прямі лінки шейряться, перезавантаження дає той самий результат), панель фільтрів зліва, сітка карток, пагінація по центру.

## 5. Відгуки

- Створення: `POST /venues/:venueId/reviews` — оцінка 1–5, текст 10–2000 символів, опційне **фото чека** (на фронті — форма під фото; MIME jpeg/png/webp, до 5 МБ). Один користувач може залишити **тільки один** відгук на заклад (уникальність venue+user, дублікат — HTTP 409).
- **Рекальк рейтингу:** після кожного створення/редагування/видалення відгуку в `venues` перераховуються `ratingAvg` (середнє числове значення, на фронті відображається зірками з кроком 0.5) і `ratingCount` — саме тому рейтинг у каталозі завжди актуальний без перерахунку «вручну».
- **Sorts:** `newest` | `oldest` | `highest` | `lowest` (передані в query `?sort=`); відгуки з `isFeatured=true` завжди вгорі списку незалежно від сорту.
- **Критик-виділення:** роль `critic` (та супер-адмін) має perm `review:feature` — `POST/DELETE /reviews/:id/feature` виставляє/знімає позначку «Рекомендований критиком». На сторінці закладу біля такого відгуку є кнопка-перемикач «Виділити/Зняти виділення»; інші користувачі цієї кнопки не бачать.
- **Мої відгуки:** `GET /me/reviews` → вкладка «Відгуки» в кабінеті (`/account/reviews`).
- **Правки/видалення:** автор — через `PATCH /reviews/:id` / `DELETE /reviews/:id` (perm `review:edit:own`); супер-адмін бачить всі відгуки в `/admin/reviews` і може редагувати/видаляти як модератор (perm `review:edit:any`). Видалення відгуку — реальне (не soft).
- Після змін інвалідується ліст-кеш закладів — рейтинг/число відгуків у каталозі оновлюються одразу.

## 6. Новини

- Хто створює: **власник закладу** (`POST /me/venues/:venueId/news`, perm `news:manage:own`) — новини свого закладу; **супер-адмін** (`POST /admin/news`, perm `news:manage:any`) — глобальні платформові новини, не привʼязані до закладу.
- Категорії: `general` (інформація), `promo` (акції), `event` (події). Статуси: `draft` → `published` → `archived`; при створенні дефолт — `published`.
- **Фото:** одне на новину (`POST /news/:id/photo`, multipart) — так само локально в `uploads/`, у проді у Blob.
- **Promoted:** поле `isPromoted` (з терміном `promotedUntil`) — піднімає новину вгору списку; виставляє супер-адмін.
- Публічні лінки: `/news` — спільний фід з фільтром по категорії, пагінація; `/news/[id]` — сторінка новини з розділом про повʼязаний заклад. На сторінці закладу — вкладка «Новини закладу»; в кабінеті власника — менеджер новин (створення, редагування, архів) зі статус-бейджами.

## 7. Повідомлення (листування)

Модуль один (`messages`), плоска таблиця з полем `kind`. Три потоки листування:

### 7.1 Користувач → менеджер закладу → відповідь
1. На сторінці закладу кнопка **«Повідомлення менеджеру»** → `POST /venues/:id/messages` — текст потрапляє власнику закладу.
2. Власник бачить список повідомлень по своєму закладу (вкладка **«Повідомлення»** в кабінеті власника `/account/venues/[id]`, `GET /me/venues/:id/messages`) і відповідає `POST /me/venues/:id/messages/:messageId/reply`.
3. Відповідь (`kind=manager_reply`) приходить автору в **вхідні**: вкладка «Повідомлення» в особистому кабінеті (`/account/messages`).

### 7.2 Користувач → підтримка (feedback) → відповідь
1. Форма **«Написати нам»** (`/contact`) → `POST /feedback` (perm не треба, логін обовʼязковий) — це вид повідомлень `kind=feedback` без конкретного адресата (recipientId = null).
2. У супер-адмінці — вкладка **«Повідомлення»**: скринька зворотного звʼязку (`GET /admin/messages/feedback`), кнопка відповіді (`POST /admin/messages/feedback/:id/reply`).
3. Відповідь (`kind=feedback_reply`) також приходить автору в його вхідні.

### 7.3 Супер-адмін → користувач (системні)
- Зі сторінки користувача у супер-адмінці кнопка «Написати користувачу» → `POST /admin/users/:id/message`. Це повідомлення `kind=system` від `senderId = null` (від імені «Пиячок») — приходить користувачу у вхідні.

**Непрочитані:** `GET /me/messages/unread-count`, позначка прочитання `PATCH /me/messages/:id/read` (доступно лише отримувачу). У хедері фронтенду для залогінених — **дзвіночок** (кількість непрочитаних, опитування раз на 60 с, «99+» при переповненні).

## 8. Скарги

- **Хто скаржиться:** будь-який залогінений користувач — `POST /complaints`. Обовʼязково один з двох таргетів — `venueId` (скарга на заклад) або `reviewId` (на відгук); причина одна з: `fake_promo` («Фейкова акція»), `fraud` («Шахрайство»), `other` («Інше»); текст від 20 символів. Статус створення — `new`.
- **Власник закладу** бачить скарги, що стосуються його закладу (таргет — сам заклад або відгук на нього), через **вкладку «Скарги» в кабінеті власника** — **лише read-only**: можна подивитися причину, тип (Заклад/Відгук), текст і дату; виправити щось він не може.
- **Супер-адмін** — вкладка «Скарги» в адмінці: список скарг із фільтром по причинах, кнопка **«Вирішити»** (`POST /admin/complaints/:id/resolve`) → статус `resolved` або `rejected` (зберігаються `resolvedBy` / `resolvedAt`). Повторний resolve — HTTP 409. Право — perm `complaint:manage` (тільки супер-адмін).

## 9. Обране (favorites)

- `POST /me/favorites/:venueId` — додати (ідемпотентно: повторний виклик — без дублювання й помилки); `DELETE /me/favorites/:venueId` — прибрати; `GET /me/favorites` — свій список (пагінація 20).
- На фронті — кнопка ♥ на карточці закладу і вкладка **«Обране»** в кабінеті (`/account/favorites`).

## 10. Пиячки (зустрічі)

Соціальна функція: користувач організовує зустріч у конкретному закладі.

- **Створення:** з модалки на сторінці закладу (кнопка зі сторінки закладу відкриває модалку): дата та час (сьогодні або майбутнє — валідація), мета зустрічі, гендер компанії (`male` / `female` / `any`), розмір групи, хто платить (`me` / `split` / `them`), бюджет. Перед створенням — обовʼязковий safety-акцепт (прапорець у sessionStorage) про безпечні зустрічі з незнайомими.
- **Статуси:** `open` → при заповненні всіх місць автоматично `filled` (з подією `hangout_filled` для аналітики); `cancelled` (скасував творець); `completed` (прошла) — закривається **cron-завданням** раз на 5 хвилин для всіх минулих по часу open/filled.
- **Приєднатися** (`POST /hangouts/:id/join`) — лише в статусі `open` і поки є місця; **вийти** (`POST /hangouts/:id/leave`) — будь-хто, крім творця; скасувати — лише творець (`POST /hangouts/:id/cancel`).
- У списку учасників персональні дані обрізаються (тільки імʼя/прізвище/дата долучення — без контактів) — мінімізація PII для безпечних знайомств.
- **Фронт:** `/hangouts` — публічний список з фільтрами (по статусах: Відкрита / Заповнена / Скасована / Завершена); `/hangouts/[id]` — деталі з учасниками і діями; в кабінеті — вкладка **«Пиячки»** з фільтром (Створені мною / Приєднані / Усі).

## 11. Аналітика

Два вимірювання: **перегляди сторінок закладів** і **події**.

- **Перегляди:** на сторінці закладу фронт fire-and-forget надсилає `POST /venues/:id/view` (з sessionId — анонімно або userId); на бекенді — **дедуплікація 30 хв** по (заклад, user/session) через ключ у Redis, тож F5 не накидає перегляди.
- **Події:** на бекенді через event-emitter записуються в `analytics_events` внутрішні події: `venue_created`, `venue_status_changed`, `review_created`, `hangout_filled` (+ `payload` jsonb).
- **Кабінет власника:** вкладка «Аналітика» (діапазон дат, дефолт — останні 30 днів): загальні перегляди, перегляди по днях, розріз подій по типах. Право `analytics:view:own` — тільки свій заклад.
- **Супер-адмінка:** вкладка «Аналітика»: **Overview** (totalViews / totalEvents / eventsByType), **timeseries** (day / week / month), **топ закладів за переглядами**, окрім того — тайловий дашборд «Огляд» (Перегляди / Події / Заклади на модерації / Користувачі / Скарги / Новини).

## 12. Фронтенд: структура і де що налаштовано

### 12.0 Загальне
- App Router Next.js 16, `src/app/**`, порт `:3001`; React 19 (включно з React Compiler). Типи відповідей API — у `src/types/*` (мапінг DTO → UI-типи в одному місці).
- **BFF-проксі:** `src/app/api/v1/[...path]/route.ts` — усі API-запити йдуть з боку фронтенда (через сеансовий cookie), токени автоматично рефрешаться; при недоступному бекенді повертається контрактний JSON-помилка (не «білий екран»).
- Картинки з бекенда йдуть через `next.config.ts` rewrite `/static/:path*` → `${BACKEND_URL}/static/:path*`.
- **Age gate 18+**: модалка «Мені є 18» / «Мені немає 18» (прапорець у sessionStorage); до підтвердження контент сторінок рендериться з атрибутом `inert` (не інтерактивний і не індексується).

### 12.1 Публічне

## 13. Інфраструктура, запуск, тестування

### 13.1 Docker (локальна розробка)
`docker-compose.yml` у кожному репо:
- бекенд: `postgres` (postgis/postgis:16) + `redis` + `migrate` (накочує міграції, сіє супер-адміна) + `backend` (NestJS, hot-reload);
- фронтенд: `frontend` (Next.js dev-сервер, mount вихідників, `BACKEND_URL=http://host.docker.internal:3000`).

При підйомі автоматично: міграції (users, venues + PostGIS, reviews, favorites, news, complaints, hangouts + participants, analytics, audit_logs, messages), сід супер-адміна; далі опціонально `pnpm seed:demo` (3 юзери, 15 закладів у статусі approved, 10 тегів, відгуки та новини з фото).

### 13.2 Прод
- **Бекенд:** Vercel (vercel.json → `api/index.ts` як serverless-вхід, `maxDuration` 30 с, memory 1024 МБ; Swagger і /static у prod вимкнені — фото йдуть у **Vercel Blob** через env `BLOB_STORE_ID` / `BLOB_READ_WRITE_TOKEN`). Деплой — vercel CLI з локального репо (не автодеплой з гіта). БД — Neon Postgres.
- **Фронт:** Vercel; URL бекенда — `BACKEND_URL` env.

### 13.3 Тестування
- **Бекенд:** Jest (unit, `pnpm test`) + e2e (supertest, `pnpm test:e2e` — стукають до живого бекенда/redis).
- **Фронтенд:** Vitest + Testing Library (unit та компонентні тести — сторінки, компоненти, `lib/`, BFF-проксі), `pnpm test`.

### 13.4 Документація API
Swagger (OpenAPI) — `http://localhost:3000/api/v1/docs` (тільки поза prod) з Bearer auth у хедері.
